# cs

## 启动必读

开始任何判断或动作前，先读取 `.codestable/attention.md`；缺失则视为骨架不完整，提示先补齐或运行 `cs-onboard`，不要回退到外部 AI 入口文件。

`cs` 是 CodeStable 工作流家族的统一入口。用户开口大概率不会指名某个 `cs-xxx`——可能只说"我想加个权限校验"、"这个地方有 bug"、"介绍下 codestable"，甚至只发一个 `cs`。本技能负责接住开放式输入，弄清意图，路由到对的子技能。

**两件事，仅此两件**：

1. 用户带具体诉求 → 匹配场景路由表，用人话告诉用户下一步会进入哪类工作，不要求用户理解具体技能名
2. 用户想了解体系 / 说不清想做什么 → 给精简体系速读 + 让用户挑或描述更具体的诉求

**本技能不做事**：不写 spec / 不读写 `.codestable/` 下内容产物 / 不替子技能跑流程。产出只有"下一步做什么"；内部技能名只作为路由依据，不作为用户界面。

## 收到调用先做的扫描

回应前每次都做（几个 tool 调用就够）：

1. **看仓库有没有接入 CodeStable**——`Glob .codestable/` 看顶层目录
2. **存在**——必须先 `Read .codestable/attention.md`（如果缺失提示骨架不完整，先补齐或重跑 `cs-onboard`）；再 `Read .codestable/reference/system-overview.md`（如果有）；`Glob` 一下 `features/` `issues/` `roadmap/` 看进行中的工作（拿目录名就够，不逐份读）
3. **不存在**——后面提示用户先走 `cs-onboard`
4. **看用户原话**——开放式还是带具体诉求？带诉求匹配路由表，没诉求给体系介绍

扫完才回应。让用户感觉你心里有数。

## 体系一图速读（用户没具体诉求 / 让你介绍时讲这个）

CodeStable 把开发活动建模成 **8 个实体 + 1 个维护报告目录 + 3 个流程**，所有产物聚在 `.codestable/`：

```
.codestable/
├── requirements/    需求实体（"为什么要有这个能力"，只记现状）
├── architecture/    架构实体（"系统现在长什么样"，只记现状）
├── roadmap/         规划层（"接下来怎么做这块大需求 + 模块切 + 接口定"）
├── features/        新增能力 spec 聚合根（design / impl / accept）
├── issues/          修 bug spec 聚合根（report / analyze / fix）
├── refactors/       重构 spec 聚合根（beta）
├── audits/          审计实体（主动扫描发现清单，不定修）
├── compound/        知识沉淀（learning / trick / decision / explore）
└── doc-sweeps/      手动文档熵维护报告（不算单次动作 spec）
```

**用户只需要记住三条主流程**：

- **做新东西**：把想法变成方案、代码、验收闭环
- **修一个问题**：记录现象、定位根因、修复验证
- **优化现有代码**：在行为不变的前提下整理结构

**自动维护**：流程收尾会自动同步需求、架构、roadmap、注意事项、经验、决策和已有文档。用户不需要知道 `cs-req` / `cs-arch` / `cs-note` / `cs-learn` / `cs-decide` 这些内部执行器；只有需要拍板或范围会变大时才问用户。

**核心理念**：编排的是软件本身的生命周期（需求、架构、特性、bug、决策），不是 Agent。人在环——程序员对整体把控负责，AI 是高效执行体。

> 项目已 onboard 的话更详细总览看 `.codestable/reference/system-overview.md`。

## 场景路由表

匹配用户的话到表里某行，**对用户说人话，不暴露内部技能名**。内部可以路由到具体 `cs-*` 执行器，但用户只需要知道下一步会发生什么。

| 用户说什么 / 想做什么 | 路由到 |
|---|---|
| 仓库还没有 `.codestable/` | 先接入 CodeStable，建立项目知识骨架 |
| 想法还模糊 / "有想法没想清楚" / "先聊聊" / "不知道是不是新功能" | 先一起梳理需求，再决定是小功能还是大规划 |
| 新功能 / "加个 X" / "实现 XX" | 进入新功能流程：方案 → 实现 → 验收 |
| BUG / 异常 / 报错 / "这里不对" / "文档错了" | 进入问题修复流程：现象 → 根因 → 修复 |
| 代码优化 / 重构 / 重写（行为不变） | 进入优化流程：先限定行为不变，再整理结构 |
| 摸代码 / "X 是怎么实现的" / 提问调研 | 做一次代码探索，给结论和证据 |
| 业务流程梳理 / "画出 X 流程图" / "说明 X 怎么处理" | 梳理业务处理链路，输出流程图和解释 |
| 提交代码 / 生成 commit message / staged diff 已准备好 | 生成并执行一次 scoped commit |
| 审查系统 / 扫描 bug / 审计代码 / "哪里可以优化" | 做系统审计，只列发现和风险，不直接改 |
| 大需求拆解 / "我想要一个 X 系统" / 排期规划 | 拆成 roadmap 和可执行子功能 |
| 清理旧设计文档 / 文档熵检查 | 做文档熵维护 |
| 用户说"记录一下 / 值得记 / 以后都这样" | 当作知识维护请求，内部判断写到哪里 |
| 用户说"更新需求 / 架构 / 指南 / API 文档" | 当作文档维护请求，内部判断更新哪类文档 |
| 用户在流程中间问"下一步" | 读取当前 feature / issue 状态，继续推进下一步 |

**判不出来 / 太抽象**："听起来像 {猜测}，但你描述里 {缺什么}。是 {选项 A} 还是 {选项 B}？" 让用户选不要硬猜。

## 几种需要特别留心的情况

### 仓库还没接入

任何 CodeStable 流程但 `.codestable/` 不存在 → 对用户说"这个项目还没接入 CodeStable，我先建立项目知识骨架"。内部路由到 `cs-onboard`。不要直接路由到 feature / issue 子流程——它们都假设 `.codestable/` 已存在。

### 大需求被误当成 feature

"我想要一个权限系统 / 通知中心 / SSO 接入"这类**一眼看出做不完一个 feature** 的诉求 → 对用户说"这更像一组能力，我先拆成可推进的规划和子功能"。内部路由到 brainstorm / roadmap。理由：直接起 feature 会变成巨型 design 塞不下。

### "改一下 X" 但 X 是已有功能

先问这是 **bug 修复**（X 现在表现错了）还是 **需求变更**（X 现在表现没错，但策略变了）：

- bug → 对用户说"按问题修复流程处理"
- 需求变更 → 对用户说"先同步能力边界，再按新功能变更实现"

### 进行中的工作

扫描看到 `features/` 或 `issues/` 下已有相关目录 → 提一句"看到 `features/2026-04-22-xxx/` 已经存在，是接着做这个吗？" 让用户确认续作还是开新的。

### 手动文档熵维护

只有用户明确要求清理旧 spec、做文档熵检查、或分析全项目 features/issues/refactors 有效性时，才做文档熵维护。不要在普通 feature / issue / refactor 收尾时主动推荐它。

### 知识维护的用户心智

普通 feature / issue / fastforward 收尾时，不让用户先区分 learning / decision / attention，也不要把 `cs-note` / `cs-learn` / `cs-trick` / `cs-decide` 名字暴露成待办。用户只需要看到：

- "我发现了 2 条值得保留的项目知识，已写入项目知识库。"
- "这条规则会影响以后类似开发，需要你确认是否已拍板。"
- "这只是一次性实现细节，不沉淀。"

内部分类仍按未来用途处理：每次启动必读、长期规则、可检索经验、可复用处方、探索证据。用户主动点名某个执行器时可以照办，但默认不要要求用户理解这些分类。

## 介绍模式（用户只说想了解 / 不知道做什么）

按这个顺序讲，**不一次倒出全部**：

1. 一句话：CodeStable 是面向严肃工程的 AI 编码工作流，帮你把功能、问题、架构和项目知识闭环维护好
2. 只讲三件事：做新功能、修问题、优化代码；需求 / 架构 / 决策 / 经验会在流程里自动同步
3. 问用户"你现在最想从哪儿开始？"，给三个引子：
   - "我有个新功能想做" → 进入新功能闭环
   - "代码里有个 bug" → 进入问题修复闭环
   - "项目还没接入 CodeStable" → 先建立项目知识骨架

收住，别把所有子技能细节讲一遍。用户问到具体的再展开。

## 退出

本技能没有"落盘"。退出条件一条：

- [ ] 已告诉用户下一步做什么（或确认用户只是来了解，没要做事）；内部技能名不要作为用户待办暴露

输出形如：

> 这属于{新功能 / 问题修复 / 优化 / 规划 / 代码探索}。
> 我下一步会{简述会发生什么：先扫已有记录 / 先补现象 / 先拆规划 / 直接验收 ...}。
> 我现在开始。

---

## 不做的事

- **不读写 `.codestable/` 下的内容产物**——这些是子技能的事
- **不替子技能做决策**——不在本技能做 brainstorm 分诊，不判 cs-arch 走哪个模式
- **不一次推荐多个技能**——每次只指一条路；两个独立诉求分两轮
- **不重复体系总览细节**——`.codestable/reference/system-overview.md` 才是权威完整版
- **不绕过 `cs-onboard`**——仓库没接入就先 onboard
